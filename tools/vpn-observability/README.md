# Мониторинг VPN

На cp-01 пользовательский systemd timer запускает сбор раз в минуту. Сборщик по SSH читает текущие счётчики Baloonz RU, Baloonz EU и Silnet и атомарно публикует их для node_exporter. История хранится в Prometheus на cp-01 согласно его настройкам; VPN-серверы не хранят историю, созданную этим сборщиком. Имена профилей попадают в метрики и Grafana, но не в журнал сборщика. Доступ к файлу метрик ограничен владельцем и группой node_exporter.

В дашборде `VPN: Baloonz и Silnet` показаны состояние служб, ресурсы и скорость сетевых интерфейсов узлов, WireGuard и трафик профилей. Профиль считается активным при росте счётчика за 5 минут: это не количество людей или устройств. Для Silnet источник даёт только суммарный трафик, для Baloonz — по направлениям. Профили Xray без идентификатора не входят в подсчёт. Сброс счётчика между опросами может привести к недоучёту. Внешние проверки Render и Craxxx в этот сбор пока не входят.

При отсутствии соединения выставляется `vpn_observer_success=0`, данные узла из очередного файла убираются; если сборщик остановился целиком, свежесть попытки истекает через 150 секунд. Из-за интервала опроса и Prometheus `rate` показания графиков усреднены за 5 минут. После включения требуются несколько циклов сбора.

Проверка: `systemctl --user status infrastek-vpn-observability.timer`, `systemctl --user status infrastek-vpn-observability.service`, затем проверить свежесть и источники в Grafana. Остановка: `systemctl --user disable --now infrastek-vpn-observability.timer`; удалить файл метрик и дашборд только при намеренном выводе мониторинга из эксплуатации. Доступ EU использует jump host Baloonz RU, внутренний адрес WireGuard и выделенный файл доверенных публичных ключей хоста в `~/.local/state/vpn-observability/ovh-known-hosts`. `HostKeyAlias` сохраняет проверку прежнего доверенного ключа EU.

Сборщик не изменяет конфигурацию VPN или ротацию логов. Для системного журнала подготовлена отдельная команда `python3 scripts/vpn-observability/apply_journald.py ИМЯ_УЗЛА`: она сохраняет предыдущее содержимое управляемого drop-in на cp-01, устанавливает лимит 250 MiB и срок до двух дней, перезапускает journald и очищает архивные журналы. При ошибке установки предпринимается откат. Лимит размера может сократить срок хранения; очистка удалённых журналов необратима. Требуются существующие sudo-права без запроса пароля.

Для ручного отката восстановить `previous.conf` из указанного каталога резервной копии в `/etc/systemd/journald.conf.d/99-infrastek-vpn.conf`; если сохранён `previous-absent`, удалить этот drop-in. Затем перезапустить `systemd-journald`. Логи Docker и отдельные файлы приложения этим правилом не ограничиваются и требуют отдельной настройки.
